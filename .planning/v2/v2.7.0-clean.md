# v2.8.x — `seedforge clean` (reversible seeding)

**Status:** Draft / future feature. Scheduled by `PATHWAY.md` as the
Wave 2 loop milestone after v2.7.0 trust work. This document is the full
design; the first implementation should ship the MVP subset described in
`PATHWAY.md`, then add manifest/cascade/recovery hardening in follow-up
v2.8.x releases.

Lets users undo a seedforge run without `TRUNCATE` so pre-existing rows
(V3-style master data seeds, manually inserted records, app-created data)
survive. The unit of reversal is a **run** — one `seedforge` invocation =
one undoable unit.

## Motivation

Today, cleanup after a seedforge run is on the user (`TRUNCATE` cascade,
manual `DELETE`, or drop-and-recreate the database). All three are
heavy-handed and wipe rows seedforge didn't create. The common ask —
"undo the last seedforge run, leave everything else alone" — has no
first-class answer.

## User-facing surface

```bash
# Default: clean the most recent run
seedforge --clean --db postgres://localhost/mydb

# Clean a specific run
seedforge --clean <run_id> --db postgres://localhost/mydb

# Clean every run seedforge has tracked
seedforge --clean --all --db postgres://localhost/mydb

# List runs without cleaning
seedforge --runs --db postgres://localhost/mydb

# Cascade through external FKs (e.g., app-created rows that reference
# seedforge rows). Off by default — errors instead.
seedforge --clean --cascade --db postgres://localhost/mydb

# Use a sidecar manifest file instead of an in-DB tracking table
seedforge --db ... --manifest ./.seedforge/last.json   # write
seedforge --clean --manifest ./.seedforge/last.json    # read + delete
```

`--dry-run` works for `--clean` too: prints the `DELETE` statements that
would run, in execution order, with row counts.

## Storage strategies

Two backends. **In-DB tracking is the default**; sidecar is opt-in.

### A. In-DB tracking table (default)

```sql
CREATE TABLE __seedforge_runs (
    run_id          uuid PRIMARY KEY,
    started_at      timestamptz NOT NULL DEFAULT now(),
    completed_at    timestamptz,
    seedforge_version text NOT NULL,
    cli_args        jsonb NOT NULL,        -- redacted: no connection string
    schema_hash     text NOT NULL,         -- sha256 of normalized DDL
    row_count       integer NOT NULL DEFAULT 0
);

CREATE TABLE __seedforge_rows (
    run_id          uuid NOT NULL REFERENCES __seedforge_runs(run_id) ON DELETE CASCADE,
    table_schema    text NOT NULL,
    table_name      text NOT NULL,
    pk_columns      text[] NOT NULL,       -- ['id'] or ['order_id','line_no']
    pk_values       jsonb NOT NULL,        -- composite-PK safe; values as JSON
    PRIMARY KEY (run_id, table_schema, table_name, pk_values)
);

CREATE INDEX idx_sf_rows_table ON __seedforge_rows (table_schema, table_name);
```

- Created lazily on first run that targets the database.
- Schema name configurable: `--tracking-schema seedforge_meta` (defaults
  to `public`). The tracking tables themselves are excluded from
  introspection so seedforge never tries to seed them.
- Cross-database parity: MySQL gets the same two tables with `JSON`
  instead of `JSONB`. SQLite gets `TEXT` for the JSON columns.

### B. Sidecar manifest file (`--manifest`)

Same content as the in-DB tables, serialized to JSON:

```json
{
  "runId": "1b2c3d4e-...",
  "startedAt": "2026-05-02T10:23:00Z",
  "seedforgeVersion": "2.7.0",
  "schemaHash": "sha256:...",
  "rows": [
    { "schema": "public", "table": "amcs",
      "pkColumns": ["id"],
      "pkValues": [["b193645b-..."], ["c66b3154-..."]] },
    { "schema": "public", "table": "orders", "pkColumns": ["id"],
      "pkValues": [["dd8049fa-..."]] }
  ]
}
```

Use case: CI fixtures where you want a manifest committed alongside the
generated SQL, or environments where adding tracking tables to the
target schema is unacceptable. If both `--manifest` and the in-DB
strategy are requested, `--manifest` wins.

## Insertion-side changes

The generator already knows the PKs of every row it produces — it has
to, for FK propagation. The change is to **also** record those PKs into
the tracking sink.

- Non-fast (multi-row INSERT) path: append to a per-table buffer, flush
  per batch in the same transaction as the `INSERT`.
- Fast streaming path (`--fast`, PG COPY / MySQL LOAD DATA): the
  streaming consumer already returns the final PK tuples for FK
  propagation (see `generate-streaming.ts`). Tee that output into the
  tracking writer — same `BEGIN`/`COMMIT` boundary as the COPY itself,
  so a crash mid-COPY leaves no orphans in the manifest.

A new `RunRecorder` interface fronts both backends:

```ts
interface RunRecorder {
  startRun(args: CliArgs, schemaHash: string): Promise<string>  // returns run_id
  recordRows(table: QualifiedTable, pkColumns: string[], pkValues: unknown[][]): Promise<void>
  completeRun(runId: string): Promise<void>
  abortRun(runId: string, reason: string): Promise<void>
}
```

Two implementations: `DbRunRecorder` and `FileRunRecorder`. The pipeline
takes one as a constructor arg; `--clean` reads from the matching
counterpart.

## Cleanup-side execution

Algorithm:

1. Resolve target run(s): `--clean` (latest), `--clean <id>`, or
   `--clean --all`.
2. Group recorded rows by table.
3. Compute a deletion order — **reverse topological order** of the FK
   graph among the affected tables. Self-referencing tables: nullify
   the self-FK column first (mirror of how generation handles
   deferred FKs), then delete.
4. For each table in order, run a single
   `DELETE FROM <t> WHERE (pk_columns) IN ((..),(..),...)`. Composite
   PKs use the `(c1, c2) IN ((v1, v2), ...)` form.
5. After all deletes succeed, delete the corresponding rows from
   `__seedforge_rows` (or remove the manifest file).
6. Reset sequences if the run was the only contributor — out of scope
   for v2.7, since detecting that requires `pg_stat_user_tables` peeking
   that's racy. Document as a known limitation.

External FK collisions (row in app-created table references a
seedforge-generated row):

- Default: abort with `SF6001` listing the offending tables and PKs.
  Hint: `--cascade` to remove dependents recursively, or update them
  manually first.
- `--cascade`: BFS through `pg_constraint` to find dependents, ask for
  confirmation listing every external table that will lose rows, then
  proceed. Records nothing in the manifest — these are app rows, not
  seedforge rows.

## Failure modes & recovery

| Failure | Behavior |
|---|---|
| Crash mid-INSERT (non-fast) | Transaction rollback. `__seedforge_runs.completed_at` stays NULL. `--clean` of incomplete runs works fine — it deletes whatever rows landed. |
| Crash mid-COPY (`--fast`) | COPY transaction rolls back; recorder transaction rolls back; nothing landed, nothing recorded. |
| User deletes manifest file but tracking table exists | Tracking table wins. Run is still cleanable. |
| Tracking table dropped externally | `--clean` errors with `SF6002`. Manual cleanup required. |
| `--clean` itself crashes mid-delete | Re-running picks up where it left off — manifest only deletes entries after the row delete succeeded for that table. |

## What ships in v2.7

- `RunRecorder` interface + `DbRunRecorder` (PG, MySQL, SQLite)
- `FileRunRecorder` for `--manifest`
- Generation pipeline: tee PKs into recorder for both batched and fast paths
- `seedforge --clean` / `--runs` / `--clean --all` / `--clean --cascade` / `--clean --dry-run`
- `seedforge --manifest <path>` on both write and read sides
- New error codes: `SF6001` (external FK collision without `--cascade`),
  `SF6002` (tracking table missing), `SF6003` (manifest schema version mismatch)
- E2e coverage: round-trip seed → clean leaves DB byte-identical to
  pre-seed snapshot (modulo sequence values, which we document); same
  test against PG, MySQL, SQLite.

## What does NOT ship in v2.7 (deferred)

- Sequence rewinding after clean
- Selective clean (`--clean --only orders` to clean only one table from
  a run) — defer until requested; the FK ordering gets gnarly when a
  partial clean leaves dangling references seedforge inserted.
- Time-windowed clean (`--clean --before 2026-05-01`) — easy to add
  later if needed.
- Manifest encryption / signing — out of scope; manifest contains PKs,
  not data.

## Open questions

1. **Default tracking schema name.** `__seedforge_runs` in `public`
   pollutes the user's schema. `seedforge_meta.runs` is cleaner but
   requires `CREATE SCHEMA` privileges. Lean toward auto-creating the
   `seedforge_meta` schema and documenting the privilege requirement.
2. **Should `--clean` work without a tracking source at all?** i.e.,
   "delete every row whose PK looks like a seedforge-generated UUID."
   Tempting but unsafe — UUIDs collide with real ones. Reject.
3. **MCP integration.** If/when the seedforge MCP server lands, `clean`
   becomes a tool the agent can call between test runs. The interface
   stays the same; MCP just exposes it. No extra design needed here.

## Success criteria

- [ ] After `seedforge --db X --count 50 && seedforge --clean --db X`,
      every table touched returns to its pre-seed row count.
- [ ] Pre-existing rows (V3-style migration seeds) are untouched.
- [ ] Two consecutive runs with different `--seed` values can each be
      cleaned independently and in any order.
- [ ] Cleaning a run with `--fast` (COPY) is symmetric — same set of
      rows removed as a batched-INSERT run with the same seed.
- [ ] `seedforge --runs` lists prior runs with timestamps, row counts,
      and the CLI args used.
